## 第一部分 — 9月9日：为什么要看最坏情况，以及怎么分析

### 1.1 核心困难：平均情况根本算不出来

这节课开篇就否定了把 **average case（平均情况）** 当作主要分析工具的做法，而且理由**不是数学上的，而是关于人的**。

平均时间与平均空间都极难确定，因为它们取决于**"平均而言输入长什么样"**——而没人知道那是什么。更麻烦的是，随着软件老化，"平均"这个词的含义会在你脚下漂移。他给了两个标志性例子：

- **搜索查询（search queries）。** 25 年前的 Google 查询就是两三个词——你按三个词来优化就行。后来 AI 来了，一个 "query" 变成了一整段个人背景描述：*"I want running shoes, these are the brands I'm interested in, this is my price range, here's my situation."* 你再也无法预测平均查询长度或它的结构复杂度，因为**用户行为在发布后几年内就彻底变了**。
- **初代 iPhone。** 它原本是设计来替代 Sony Walkman 的**音乐播放器**，手机是后来因为大家抱怨要带两台设备才"拼"上去的。设计它的人根本想不到 App Store、拍照用途、照片数量、离线影音库。开发者基于一堆假设把它做出来，用户立刻开始用它做从未被设计过的事。后果很具体：**因为没预料到的照片存储，设备内存被撑爆**，整个设计不得不重做。

> **"So when you design software, you have no idea what people will do."**
> （所以你做软件的时候，根本不知道人们会拿它干什么。）

普遍的教训是：你针对一个假设的问题去构建，用户拿一堆没测过的问题来攻击它，系统在没人预料到的量级上崩掉，你回去重新设计。**"This is the general problem, and it is always going to be there."**（这是普遍问题，永远都会存在。）

### 1.2 为什么最坏情况可做

选 worst case 不是因为它悲观，而是因为它**可以被形式化（formalizable）**。它要的是**最大可能的负载**，而在很多领域，这个最大值是一个已知的固定数：

| 领域 | 有界的最坏情况 |
|---|---|
| 视频流媒体 | 每个用户每天 24 小时观看 × 订阅用户数 → 总下载小时数 |
| 动作游戏 | 人的输入速度：玩家物理上能多快按下按键？这决定了响应时间要求的上限 |
| 金融／交易所 | 上市标的数量 × 更新频率（每秒或每 10 秒一次）—— *"worst case, every stock is trading every time"* |
| 嵌入式系统 | 固定的内存预算 |

他自己的轶事把这一点讲得很清楚：他的孩子下载的电影**比他们五年内能看完的还多**，因为**下载速度远快于观看速度**。所以就按"每人每天 24 小时"来设计——**"it won't happen, because nobody has 24 hours to watch, but that's the idea."**（这不会发生，因为没人有 24 小时看片，但这就是思路。）

### 1.3 我们究竟在测量什么

两个资源，而且它们互相冲突：

- **Running time（运行时间）**——大多数算法把输入数据转换成输出数据，运行时间通常随输入规模增长。
- **Space usage（空间占用）**——算法需要空间来存放中间结果。

两个重要补充：

- **空间占用随实现选择剧烈变化**，尤其是 **iteration（迭代）vs recursion（递归）**：每一次递归调用都会压入一个新的 stack frame（栈帧），只有在返回时才弹出。所以**递归深度直接驱动空间占用**，而它跟算法的设计绑定。（他提到后面讲 tree 时递归深度不会很大——"5, 6, even 10"——但栈的问题在实践中确实会咬人。）
- **平均空间和平均时间一样难确定**，同样转向最坏情况。空间和时间一样，是**输入规模的函数（a function of input size）**。

更快几乎总是要付出空间。**"You can't have both. You can't be faster and use less space to save time."**

### 1.4 方法一：实验（经验）研究

课件给出的流程：

1. **Write program implementing the algorithm**——写程序实现算法。
2. **Run program with inputs of varying size and composition**——用**规模和构成都变化**的输入运行。
3. **Use a method like `System.currentTimeMillis()` to measure actual running time**——测量实际运行时间。
4. **Plot the results**——把结果画出来。

**计时机制。** 最天真的做法是 `System.currentTimeMillis()`：一个返回自 1970 年 1 月 1 日以来毫秒数的系统调用，两次读数相减就得到耗时。这**只在你独占的机器上**才有效。在共享服务器、云上、或学校机房上，它测到的竞争（contention）和你代码的耗时一样多：早上跑很快；午饭时间大家都在编译，你"all of a sudden you crawl"（突然就爬了）。

正确的做法是**向操作系统索取你这个进程实际消耗的 CPU 时间**。操作系统会不断抢占和重新调度你的进程——**"it may go in and out 1,000 times before it's finished"**——但它会记录你的进程**被允许运行**了多少 CPU 时间，所以这个测量不受其他用户影响。注意这**不是** wall-clock time（挂钟时间）：你可能在系统里待了三小时，却只累积了十分钟 CPU 时间，而且是一毫秒一毫秒地攒起来的。

**图长什么样。** 一张典型的实验图（输入规模 0–100 对运行时间）上升得比线性更快——看上去像多项式或指数。输入翻倍，运行时间可能是四倍。

**那个反直觉、也正因如此必须做实验的结果。** 对于**很短**的列表，朴素的 linear search（线性查找）会打赢看起来更聪明的 binary search（二分查找），因为二分查找要额外付出常数开销（切分、比较、递归），而这些开销在三个元素上根本无法摊薄。这就是他断言你会**在操作系统内核代码里看到直接的线性查找**的原因，尽管二分查找在渐近意义上更优：内核的列表很短，短列表上"笨"算法赢。手工排序三个元素几次比较就够了；对三个元素用二分查找纯属折腾。他的说法是：*"Long list, binary search is a Ferrari. Short list, you're walking."*（长列表里二分查找是法拉利，短列表里你就是在走路。）**实践结论是：你必须做实验才能知道自己处在哪个区间。**

**课件列出的四条局限：**

1. **Need to implement algorithm**——必须实现算法；这很难，而且实现出来可能发现思路本身不行（*"may be difficult and the algorithm may prove inadequate"*）。
2. **Results may not be indicative of the running time on other inputs** not included in the experiment——结果未必能代表没被测到的输入。
3. **Comparing algorithms requires the same hardware and software environments**——比较算法必须统一软硬件环境。你不能让每个学生用自己的笔记本计时，**"some might be using the supercomputer"**。必须固定机器。
4. 由此推广：**输入数据本身也必须归一化**——不只是规模相同，而是**同一份数据**。否则一个学生排序她的列表、另一个排序他的列表，比较就毫无意义。

他对此的收尾评价，正是理论分析胜出的理由：为了发现三个版本里有两个不行而把三个都实现出来，成本太高——**"each one takes you a week to write; you don't have that much time."**

### 1.5 方法二：理论分析

不实现，而是拿**算法的高层描述**，数 primitive operations（基本操作），定出 **complexity class（复杂度类别）**。课件给的四个步骤：

1. **Express algorithm as pseudo-code**——把算法表达成伪代码。
2. **Count primitive operations**——数基本操作。
3. **Describe algorithm as f(n)**——描述为 f(n) 的函数，其中 *n* 是 *"a property of the input with significant impact on performance"*（对性能有显著影响的输入属性），也就是输入的**规模**。
4. **Perform asymptotic analysis**——做渐近分析，用 asymptotic notation（渐近记号）表达。

**它为什么赢：**

- **独立于软硬件环境**，因此是**公平、一致的算法比较基础**，并且可跨机器迁移。
- **考虑所有可能的输入**——至少是所有"坏"的输入。
- 它有时能证明 **optimality（最优性）**——即没有算法能做得更好。他预告讲排序时会带全班做这件事：***"can you go any faster?"*** 它还具有诊断价值：如果分析结论说思路不对，**"you can throw it out the window and start again"**，而不是白花一周去实现。

> **"buying a bigger computer is not going to make the algorithm better — you just run it on a faster machine."**
> （买一台更大的电脑不会让算法变得更好——你只是把它跑在了一台更快的机器上。）

硬件升级只是把一个 **constant factor（常数因子）** 乘到 `T(n)` 上，**不改变增长率**。所以常数因子在分析中会被丢掉。

### 1.6 伪代码约定

Pseudo-code 是让"数操作"得以进行的桥梁，它的定位很精确：**比英文散文更有结构，比程序更少细节**。它不能编译，但长得像一门语言，所以会编程的读者能立刻读懂，并且**关键地——不用实现任何东西就能数出操作次数**。

课件第 11 页直接给出了记号：

| 结构 | 记号 |
|---|---|
| Control flow（控制流） | `if … then … [else …]`、`while … do …`、`repeat … until …`、`for … do …` |
| Indentation（缩进） | **取代花括号**（`begin`/`end`、`{`/`}`） |
| Method declaration | `Algorithm method(arg [, arg…])`，并描述 `Input:` 与 `Output:` |
| Method call | `method(arg [, arg…])` |
| Return value | `return expression` |
| **赋值 Assignment** | `←`（相当于 Java 的 `=`） |
| **相等判断 Equality testing** | `=`（相当于 Java 的 `==`） |
| Expressions | 数学排版，例如 n² |

缩进这条是刻意的：它呼应 Python。他顺势用 Python 的空白字符坑当作警示——**人眼在屏幕上分不清空格和 Tab**，所以"缩进不对，可它看起来完美"。

### 1.7 例程：求数组最大值

这是贯穿两次课的 running example，值得写准确：

```
Algorithm arrayMax(A, n)
Input:  array A of n integers
Output: maximum element of A

currentMax ← A[0]
for i ← 1 to n - 1 do
    if A[i] > currentMax then
        currentMax ← A[i]
        { increment counter }
return currentMax
```

对应的 Java 版本逐行相同，只有一个实际差别：**Java 里数组自带 `A.length`，所以不必传 `n`；而 C 语言必须把长度和数组一起传进去。**

**两种解法，以及为什么"显然的那种"是错的。** 课件第 42–43 页把这件事当作一个刻意的教学点：

- **方法一：扫描一遍。** 把当前最大值初始化为第一个元素，走一遍数组，遇到更大的就更新。时间复杂度**关于 n 线性**——一趟，每个元素一次比较。
- **方法二：先排序，再返回最后一个元素。** 写起来**容易得多**，因为排序可以直接调库：`sort(A); return A[n-1];`。但排序比扫描更贵，所以**更慢**，而且数组越长差距越大。

这就是老师要学生内化的普遍模式：**容易写出来的算法，往往就是慢的那个**；而"实现一个算法有多难"与"它有多贵"是**两件正交的事**。

他补了一层关于伪代码的次要观点：真正的琐碎错误都发生在写 Java 版本的时候——index out of bounds（数组越界）、把 `i = 0` 写成 `i = 1` 造成的 off-by-one——**"you spend an hour on something really small because you keep making little mistakes."** 而这类改动 *"won't change the complexity of the item"*（不会改变算法的复杂度）。代码对这类编辑是宽容的，但它会吃掉真实的调试时间，而伪代码分析不会。

### 1.8 数基本操作

**定义。** Primitive operation 是算法执行的一个基本计算，可以在伪代码中识别出来。

**课件第 13 页的清单：** 给变量赋值、调用方法、做算术运算、判断条件、数组索引、跟随对象引用、从方法返回。

**支撑整个方法的两条假设：**

1. **每个基本操作都假设耗时恒定（constant amount of time）。** 不去追究某个操作在特定语言、特定硬件上的精确耗时。老师明确说：`x = y` 在 C、Java、Python 里耗时确实不同——但既然**所有算法都在同一台机器、同一种语言上比较**，这个成本就互相抵消了。**"The exact definition is not important — later we will see why."**
2. 真正数的是**每个操作随输入规模执行的次数**，仅此而已。

**课件第 14–17 页的计数规则：**

| 代码片段 | 基本操作数 |
|---|---|
| `int num = 10;` | 1 —— 赋值 |
| `int num = A[10];` | 2 —— 数组索引 + 赋值 |
| `if (num < 10)` | 1 —— 条件判断 |
| `if (num < A[10])` | 2 —— 索引 + 条件判断 |
| `while (i < 10) { … }` | 每轮 1 次 **+ 1**（最后一次判断失败的那次） |
| `do { … } while (i < 10)` | 每轮 1 次 |
| `for (int i = 0; i < n; i++) { X ops }` | `1 + (n+1) + n + n·X` |

`for` 循环的拆解**值得背下来**，因为后面 arrayMax 的计数用的就是它：

- `int i = 0` —— 执行 **1 次**
- `i < n` —— 求值 **n + 1 次**（n 次成功 + 1 次终止失败）
- `i++` —— 求值 **n 次**
- 循环体内每条语句 —— 各求值 **n 次**

注意 9月9日 录音里强调的数组规则：**数组赋值算两次操作**——一次算地址、一次拷贝值。

### 1.9 把 arrayMax 写成 f(n)

`Lecture4_AnalysisTools.pdf` 第 18 页把计数列成了表：

| 伪代码行 | 操作数 |
|---|---|
| `currentMax ← A[0]` | 2 |
| `for i ← 1 to n - 1 do` | 1 + 2·n |
| `if A[i] > currentMax then` | 2·(n − 1) |
| `currentMax ← A[i]` | 2·(n − 1) |
| `{ increment counter }` | n − 1 |
| `return currentMax` | 1 |
| **Total（合计）** | **7n + lower order terms** |

所以 arrayMax 在最坏情况下最多执行 **7n** 次基本操作。课件随后给出夹逼：设 *a* 为最快基本操作的耗时、*b* 为最慢的，

> **a · 7n ≤ T(n) ≤ b · 7n**

也就是说运行时间被**夹在两个线性函数之间**。常数因子 7 是真实存在的，但它毕竟只是个**常数**——下一次课整场都在说明为什么它不重要。

## 第二部分 — 9月11日：增长率、标准复杂度类别与渐近分析

### 2.1 为什么看增长率，而不是运行时间

这节课用上一节的结论开场。同一个算法、同样的输入，跑在快机器和慢机器上，**绝对运行时间不同，但增长率相同**。如果它是线性的，那么在两者上都是线性的：输入翻倍，时间翻倍。

> **"The growth rate of running time is an intrinsic property of the algorithm, not the machine you run it on."**

这就是"换更快的硬件"不能回答算法问题的原因，也是这个单元如此定位的原因。他重申了范围：本单元覆盖 **abstract data types *以及* 它们实现的效率**。写 contract（`push`、`pop`、`size`、`isEmpty`）是最容易的部分——***"anybody can write the contract."*** 底层怎么实现才是 **critical**，而算法内容正住在那里。

### 2.2 标准复杂度类别，各配一个例子

`Lecture4_AnalysisTools.pdf` 第 21 页标题是 **Seven Important Functions**，但实际列了八个（第八个 factorial 被标注 *"// not so often"*）。课上每讲一个都挂了具体实例：

| 类别 | 名称 | 课上的典型例子 |
|---|---|---|
| **1** | Constant 常数阶 | **数组索引查找。** 你给下标，机器算地址、取值。时间固定，与规模无关。 |
| **log₂ n** | Logarithmic 对数阶 | **二分查找**（仅适用于**已排序**列表）。n = 1,000 时约需 **10** 次查找，因为 2¹⁰ = 1,024，每步搜索范围减半。 |
| **n** | Linear 线性阶 | **打印整个列表。** 必须访问每个元素。"The complexity is not any greater, but not any less."（复杂度不能更高，也不能更低。） |
| **n log₂ n** | N-Log-N 线性对数阶 | **排序。** 为什么排序落在这里留到排序课讲，但形状现在就断言了。 |
| **n²** | Quadratic 平方阶 | **矩阵转置或拷贝。** n×n 矩阵有 n² 个元素，每一个都得动。 |
| **n³** | Cubic 立方阶 | **三层等长嵌套循环。** |
| **2ⁿ** | Exponential 指数阶 | **枚举所有 n 位布尔函数**——一共有 2ⁿ 个。 |
| **n!** | Factorial 阶乘阶 | **旅行商问题的穷举搜索。** |

他围绕这份清单强调三点：

- **这些是基本的积木。** 真实算法是它们的**组合**——**"as they get more complex, they will have parts which have different complexities."** 他给的实用启发式：看到三个同规模的循环就预期 O(n³)；看到 `for i = 0 to 100` 就知道它跑 100 次。**最内层循环的执行次数 = 所有外层循环迭代上限的乘积。**
- **多维结构的元素个数相乘。** 维度为 n × m × l 的结构有 n·m·l 个元素；等边时可写作 n³。他指出内存是线性的，所以矩阵必须以**平铺的列表**存储；编译器依据下标、元素大小和已知维度算出元素地址——这正是 C/C++/Java 里**必须声明元素类型**的原因。
- **指数阶是实践意义上的天花板。** ***"It's not an exception, but it's uncommon. That's usually as bad as it gets, unless you have a very peculiar problem — and then you might get factorial."***（它不是例外，但不常见。通常它就已经是最坏的了；除非你碰到非常特殊的问题，那才可能到阶乘。）

### 2.3 为什么高阶复杂度真的要紧：旅行商问题

TSP 讲了很久，因为它是这节课"复杂度分析有真实杀伤力"的证明。

**问题本身。** 一个推销员要拜访所有有客户的城市，然后回家，并且尽量少烧油。路线排列数是城市数的**阶乘**。他用小例子建立直觉：3 个城市可以走 1‑2‑3 或 1‑3‑2；加到 4 个，排列空间就**炸开了**。

**IBM PC 实验。** 他在 1980 年代初买了最早期的 IBM PC 之一，写了穷举搜索——生成所有可能的路线、把距离加起来、取最小——结果发现大约能处理 **16 个城市**，再多就懒得等了。

**他带着全班做的算术。** 如果 10 个城市要 6 秒，那么 11 个城市要 6 × 11 = 66 秒；12 个城市要 66 × 12 ≈ 792 秒；依此类推。**每多一个城市，时间就乘以一个大于 10 的数。** 仅仅再多加 6 个城市，你就慢了**一百万倍**。

**现代的答案。** 今天的机器大约快了 **100,000 倍**（他的估计：当年是千赫兹级别，现在约 5 GHz）。这把你从 16 个城市带到了大约 **20 个**。二十个。（核对一下：20!/16! = 116,280，正好约等于这个 10 万倍。）而 **"30 cities is never going to happen"**——*"the numbers you're looking at are 10 to the power of… it's just gone."* 这是整节课最重要的对比：**一次巨大的硬件飞跃，只买到了小得可笑的算法进步。**

> **"If you look at the complexity, you've gotta feel for how bad this is going to be before you even test it."**
> （看复杂度的时候，你得在动手测之前就先感受到它会有多糟。）

**实践上的出路——近似。** 正确的教训不是"TSP 无解"：

> **"It doesn't mean that you can't have a good solution. It just means you can't have a perfect solution."**
> （这不意味着你得不到好的解，只意味着你得不到完美的解。）

他给出的启发式例子是 **nearest-neighbour tour（最近邻路线）**：从当前位置出发，每次去最近的未访问城市，重复。它几秒钟就能给出一条合理路径，结果落在最优解的 **约 10% 以内**。够用了，而代价只是极小的一部分。

**TSP 类问题真实出现在哪里**（这也是他坚持工程方向学生会遇到它的原因）：

- **喷墨打印机字头路径规划。** 字头要在成千上万个像素位置落墨；像老式打字机那样来回移动极其低效。把同一区域的点一次打完再移动——**这就是 TSP**。
- **硅芯片线路布线。** 子电路之间的互连用**金**来做（因为金不生锈、不腐蚀），而金很贵，所以要最小化总布线长度。
- **机器人路径优化。**
- 激光打印机历史上也有同样的问题。

### 2.4 数字：复杂度到底值多少钱

这一节是要**背下来的**，因为老师明说了他会考。

**增长表（n 从 8 翻倍到 512）：**

| n | log₂ n | n | n log₂ n | n² | n³ | 2ⁿ |
|---|---|---|---|---|---|---|
| 8 | 3 | 8 | 24 | 64 | 512 | 256 |
| 16 | 4 | 16 | 64 | 256 | 4,096 | 65,536 |
| 32 | 5 | 32 | 160 | 1,024 | 32,768 | ~4.3 × 10⁹ |
| 64 | 6 | 64 | 384 | 4,096 | 262,144 | ~1.8 × 10¹⁹ |
| 128 | 7 | 128 | 896 | 16,384 | 2,097,152 | ~3.4 × 10³⁸ |
| 256 | 8 | 256 | 2,048 | 65,536 | 16,777,216 | ~1.2 × 10⁷⁷ |
| 512 | 9 | 512 | 4,608 | 262,144 | 134,217,728 | ~1.3 × 10¹⁵⁴ |

他要学生读出两个结论：

- **log n 完全不在一个星球上。** 从 n = 8 到 n = 512，输入乘以 64，而 log₂ n 只从 3 涨到 9——**只翻了三倍**。**"If the complexity is log n, doubling the input is nothing."**
- **n = 512 时 2ⁿ ≈ 10¹⁵⁴。** 宇宙年龄量级是 10¹⁷ 秒（课件给的数是 **4.42 × 10¹⁷ 秒**，即 140 亿年）。你**不可能**执行 10¹⁵⁴ 次操作。**时间根本不够。**

**反过来问——固定时间预算能做完多少活？** 课件把表倒过来用，这往往是更有用的框架：

| 复杂度 | 一小时能完成的工作量 |
|---|---|
| 4·10⁸·n | **9,000,000** 次操作 |
| 2ⁿ | **31** 个元素 |

他自己举的"稻草人"例子——400n 那个函数——一秒钟能做完 25,000 个任务，一小时 900 万个，轻轻松松。而指数复杂度在**同样一小时**里只能处理 **31 个元素**。

**那个"看起来无害的循环"陷阱。** 课件第 29 页是个刻意的陷阱，他明说这会被考。仔细读：

```
n ← 64
k ← 1
for i ← 0 to n-1 do
    for j ← 0 to k-1 do
        pick()
        { increment counter j }
    k ← k * 2
    { increment counter i }
```

一眼看上去你会说 O(n·k)，或者若 n = k 就是 O(n²)。**完全不是。** 在 n 轮外层迭代中，**k 每轮翻倍**——所以内层循环跑 1、2、4、8……次，这是一个等比级数，总和约为 2ⁿ。当 n = 64、每秒十亿次操作，课件给出的结论是：**要跑 585 年。**（核对：2⁶⁴ / 10⁹ 秒 ≈ 1.8 × 10¹⁰ 秒 ≈ 585 年。）普遍教训：**循环的复杂度不是你能看见的那个循环上界，而是那个上界随算法推进如何演化。**

**那张骗人的图。** 把 insertion sort（n²/4）和 merge sort（2n log₂ n）画在一起，在较小的 n 上看起来几乎一样。到一百万条数据时，差距是压倒性的：

| | Insertion sort —— n²/4 | Merge sort —— 2n log₂ n |
|---|---|---|
| 在慢机器上 | **约 70 小时** | **约 40 秒** |
| 在快 100 倍的机器上 | 约 40 分钟 | **不到 0.5 秒** |

他补了商业上的后果：在云服务器上你是**按使用时间付费的**。快 100 倍的情况下，你是在"付 40 分钟"和"付半秒"之间做选择。图之所以骗人，是因为它只展示了小 n 区域——那里两条线看起来都是直的；而红线"keeps going faster and then…"（会越来越快，然后就……）。

### 2.5 渐近分析：我们丢掉什么，为什么能丢

**Asymptotic behaviour（渐近行为）**是 n 无界增长时的极限行为。讲课很坦率地说我们并不生活在无穷处——**"we don't live with infinity in real life"**——实践目标是百万、十亿量级的 n，那已经足够大，渐近结论已经接管了。

**低阶项（lower-order terms）。** 比较 n、n + 1000、n²、n² + 10⁴n。那些多出来的项只在**小 n** 时有意义：n = 1000 时，给 1000 加 1000 就是翻倍；等 n 到了一百万，加 1000 已经看不见了——**"they meet"**（它们重合了）。所以低阶项被丢掉。

课件第 32 页直接问：**can we safely ignore lower-order terms like this?** 答案是**在 n 很大时可以**——但有一个他明确点出、并且解释了一个他被问过的设计问题的例外：***"why would you use a list if you can use an array?"***（既然能用数组，为什么还要用链表？）因为**在小规模列表上，看起来更好的算法实际上可能更差**。如果你的程序管理的是一个小列表——就像操作系统内核那样——那么渐近意义上"难看"的算法可能靠常数开销赢回来。***"It depends on the problem size."***

**常数因子（constant factors）。** 画一张 **log-log plot**（横轴 log n，纵轴 log f(n)），把 n³ 和 n³/10⁶ 画在一起：两条都是**斜率恰好为 3 的直线**，只差一个常数偏移。原因很代数：log(n³) = 3 log n，**指数就是斜率**，而除以 10⁶ 只是平移了截距。同理 2ⁿ 和 2ⁿ/10⁶ 行为一致，因为 10⁶ ≈ 2²⁰，所以 2ⁿ/2²⁰ = 2^(n−20)——取对数后只差一个常数 20，而它无关紧要。

而最杀手级的论点：**常数因子是可以用钱买掉的。** 某个实现慢几倍？买一台快几倍的机器，差距就没了。但**糟糕的增长率是买不掉的**——这正是整个 TSP 故事的要点。

**统一规则（课件第 38、45 页）：** 既然常数因子和低阶项在大 n 下不影响增长率，**在数基本操作时就把它们忽略掉**，结果用渐近记号表达。

### 2.6 大 O 记号（Big-O notation）

到这里课程交棒给形式化工具，课件同时给出了定义和完整证明。

**定义（第 39 页）。** 给定函数 f(n) 与 g(n)，我们说 **f(n) is O(g(n))**，如果存在正常数 **c** 和 **n₀** 使得

> **f(n) ≤ c · g(n)，对所有 n ≥ n₀**

也就是当 n **足够大**之后。等价的说法是：f(n) 是 **函数集合 O(g(n)) 的成员**。

**它是什么意思（第 44 页）。** Big-O 给出的是**增长率的上界**。"f(n) is O(g(n))" 意思是 f(n) 的增长率**不超过** g(n) 的增长率。因此它**按增长率给函数排序**：

| 关系 | f(n) is O(g(n))? | g(n) is O(f(n))? |
|---|---|---|
| g(n) 增长更快 | **Yes** | No |
| f(n) 增长更快 | No | **Yes** |
| 增长相同 | **Yes** | **Yes** |

注意最后一行的对称性：所谓"增长相同"就是互为 O——所以这里定义的 Big-O 在界紧的时候并不区分 f = Θ(g) 与 f = O(g)。

**经验规则（第 45 页）。**

- 若 f(n) 是 d 次多项式，则 **f(n) is O(nᵈ)**——丢掉低阶项，丢掉常数因子。
- **Use the smallest possible class**：写 "2n is O(n)"，不写 "2n is O(n²)"（虽然后者技术上是对的）。
- **Use the simplest expression of the class**：写 "3n + 5 is O(n)"，不写 "3n + 5 is O(3n)"。

**三个证明范例（第 46 页）。**

*例 1：7n − 2 is O(n)。* 需要 c > 0、n₀ ≥ 1，使 7n − 2 ≤ c·n 对 n ≥ n₀ 成立。**取 c = 7、n₀ = 1 成立。**

*例 2：3n³ + 20n² + 5 is O(n³)。* 需要 c > 0、n₀ ≥ 1，使 3n³ + 20n² + 5 ≤ c·n³ 对 n ≥ n₀ 成立。**取 c = 4、n₀ = 21 成立。**

*例 3：3 log n + 5 is O(log n)。* **取 c = 8、n₀ = 2 成立。**

**第 47 页给出了找这些常数的流程，这是要考的技能：**

1. 从 f 中**丢掉低阶项**。
2. 从 f 中**丢掉常数因子**——此时你得到了临时的类别。
3. 找出**"最小"的函数类别**，并用它**最简单的表达形式**。
4. 求出 **c** 的值——课件原话：*"look at coefficients in front of lower-order terms; the sum of positives is usually a good start."*
5. 由 c 反推一个小 **n₀**，用代数算出来或"by eye"（目测）。

**用到 arrayMax 上（第 42 页）。** arrayMax 最多执行 7n 次基本操作。常数因子 7 被忽略，低阶项也被忽略。你需要 n 和 c 使 n ≤ c·n 在 n ≥ n₀ 时成立；c ≥ 1、n₀ ≥ 0 即可。所以：**arrayMax runs in O(n) time.**

**一个反例（第 43 页）。** n² **不是** O(n)。若 n² ≤ c·n 对 n ≥ n₀ 成立，两边约掉 n 得 n ≤ c——这不可能，因为 c 是常数而 n 无界。图上 n² 会永久地把 100n 和 10n 甩开。

**以及他布置的那个推导（详见第三部分）。** 设定是这样的：你有一个**已排序的链表**，要把新元素插入正确位置。为了找到位置，你必须边走边比较。平均而言你要检查**半个**链表——**n/2 次比较**——因为插入点落在左半和右半的概率相同。

由于链表长度从 1 增长到 n，第 i 次插入大约需要 i/2 次比较，所以总数是

> 1/2 + 2/2 + 3/2 + … + n/2 = (1/2) · n(n+1)/2 = **n(n+1)/4**

课件把它记为 **n²/4**，渐近上即 **O(n²)**——这也正是同一份课件后面把 insertion sort 写成 n²/4 的来源。他带着全班仔细走了这一步，然后把话说得很直白：这个推导**会作为练习，而且可能进考试**。AI 可以**帮**你做，但你必须先把问题向 AI 描述清楚，并且自己能够复现——**"if you just rely on AI, there's no AI in the exam."**（如果你只依赖 AI，考场上可没有 AI。）

这两张表是为了给学生一个**可感知的**尺度，老师也明确这么定位。第 34 页用人类历史做"停止时间"参照，第 35 页是计算机真实的开销。

**时间尺度（第 34 页）：**

| 事件 | 秒数 | 科学计数法 |

**操作开销（第 35 页，标题 "Operation Time"）：**

| 操作 | 时间 |
|---|---|
| L1 cache 访问 | 0.5 ns |
| **分支预测失败 Branch mispredict** | **5 ns** |
| L2 cache 访问 | 7 ns |
| Mutex 加锁／解锁 | 25 ns |
| **主存访问 Main memory reference** | **100 ns** |
| 用廉价算法压缩 1 KB | 3,000 ns |
| 在 1 Gbps 网络上发送 2 KB | 20,000 ns |
| 从内存顺序读取 1 MB | 250,000 ns |
| 同一数据中心内的往返 | 500,000 ns |
| **磁盘寻道 Disk seek** | **10 ms —— 课件批注："was 30 ms in 1980!!"** |
| 从磁盘顺序读取 1 MB | 20,000,000 ns（20 ms） |
| 加州 → 荷兰 → 加州 发送一个包 | 150,000,000 ns（0.25 s） |

**为什么这些硬件题外话是必要的。** 他花了不少时间讲分支预测和缓存，因为这解释了**为什么"基本操作模型"是一种理想化**：

- **流水线（Pipelining）。** CPU 不可能同时用上所有功能单元——*"currents, voltages, stuff has to stabilize before you can read the answer, right? This is why the clock speed is what it is: nothing happens instantly."*（电流、电压这些东西必须先稳定下来你才能读到答案。这就是时钟频率只能是现在这样的原因：**没有什么是瞬间发生的**。）所以当一条指令在等待时，硬件会投机性地预取它**预测**接下来要用的东西。这就像工厂流水线：你不会等上一道工序完全结束才开始准备下一道。
- **分支预测（Branch prediction）。** 遇到 `if` 时，编译器／运行时依据模式猜你会往哪边走（"most of the time `if i > 1000 then break` is false"）。猜对了，投机做的工作就是白赚的；**猜错了必须把做的工作全部丢掉重来——代价 5 ns**。现代预测器非常好，恰恰是因为有海量数据可学。
- **缓存行（Cache lines）。** 从 RAM 取一个整数，不会只取一个整数：它会把大约 1 KB 拉进 L2、把约 100 字节拉进 L1，赌的是"**if you access this, you are probably going to access something next to it.**" （如果你访问了这个，你很可能接着访问它旁边的东西。）这是个赌注，也正是 L1（0.5 ns）和主存（100 ns）相差 200 倍的原因。
- **磁盘。** 从磁盘读 1 MB 之所以要 20 毫秒，主要由**盘片转速**和机械结构决定——这就是这个数字"40–50 年几乎没改进"的原因。他解释了磁记录机制（强磁场使磁畴取向，取向方向编码 0 和 1），以及相对运动的要点：磁头掠过旋转盘片，等价于盘片在固定磁头下旋转——他用的比喻是**飞机在跑道上降落**。

**综合起来：** 模型把每个基本操作都当作常数时间；而硬件表说明这个"常数"实际上横跨大约**九个数量级**（0.5 ns 到 0.25 s）。模型之所以还能成立，是因为我们**在同一台硬件上比较算法**，常数互相抵消——和 §1.8 是同一个论证。

### 2.8 接回 ADT：`Lecture3_ADTs.pdf`

9月11日下半场打开了这份课件，它的目的是把"实现选择"和上面的效率论证连起来。

**ADT 为什么存在（第 3 页）——"抽象"带来的好处：**

- **Behavioural contract（行为契约）**——这个类型对外承诺什么。
- **Encapsulation（封装）**——实现细节被隐藏。
- **Isolation（隔离）**——用户代码和 ADT 实现可以各自独立修改而互不影响。
- **Flexibility（灵活性）**——不同的实现可以**互换**，并且各自可以针对特定目的优化。

**Stack ADT（第 4 页），原文照录：**

```java
package neu.adt;
import java.util.NoSuchElementException;

public interface Stack<T> {
    public void push(T element);
    public T pop() throws NoSuchElementException;
    public T top() throws NoSuchElementException;
    public int size();
    public boolean isEmpty();
}
```

课件留了一个值得回答的设计问题：**只使用已有的 `push()` 和 `pop()`，你如何实现 `top()`？**（先想清楚 `pop` 究竟承诺了什么再作答——这是一道经典的"契约到底保证什么"的题。）

**泛型与类型擦除（第 5–6 页）。** 客户端写 `Stack<String> stack = new StackImpl<>();`、`stack.push("A String")`、`String str = stack.pop()`。课件把 `StackImpl` 标为 **concrete data type（具体数据类型）**。关键在于它随后展示了**编译期**接口长什么样：类型参数消失了，`String` 被直接代入——`public void push(String element)`、`public String pop()`。这就是 Java 的 **generics erasure（泛型擦除）**，老师的要点是：抽象是**编译期的便利**，不是运行期机制。

**实现选择（第 7 页）。** ***"Remember that an Interface has to be implemented — a design decision."***（记住接口必须被实现——这是一个设计决策。）

- ADT 用 **arrays 或 linked data structures** 实现。
- 很多 ADT 两者皆可。
- 有些需要两者结合。
- ADT 常常用其他 ADT 来实现。

**四种常见链式结构（第 8 页）：** singly linked list（单向链表）、doubly linked list（双向链表）、circularly linked list（循环链表）、tree（树）。

**课上已经见过的具体代码**——`ListNode<T>` 含 `element` 与 `next`；`LinkedList<T>` 含 `head`、`tail`、`size`；以及 `addFirst`、`addLast`、`removeFirst`。`removeFirst` 里有两个细节值得注意：空表这个特殊情况返回 `null`，以及当 `size` 归零后必须把 `tail` 重置为 `null`。`addLast` 里则有镜像的特殊情况，注释写着 *"here if added to empty list."* **这些特殊情况恰恰就是后面引入循环链表的原因。**

**权衡表——这是整份课件的分析核心。** 第 15–24 页比较单向、双向、循环链表，模式是：**每一项能力都要用内存或指针维护成本去换。**

| 能力 | 单向链表 | 双向链表 |
|---|---|---|
| 遍历方向 | 只能 head → end | **双向**（例如浏览器前进／后退） |
| 在给定节点**之前**插入 | 必须遍历找到前驱——低效 | **直接**通过 `prev` 指针完成 |
| 反转整个链表 | 必须重新指派每个 `next` 指针 | **直接**，两个指针都在手 |
| Deque（两端插入／删除） | 较低效——可能要遍历到另一端 | **天然契合** |

而代价（第 19 页）说得很简单：每个节点为了额外的 `prev` 指针付出**额外的内存**——*"significant if memory is a concern, especially in environments with limited resources"*——以及插入／删除时需要维护所有指针带来的**更高复杂度**。

**循环链表（第 20–24 页）** 有三个理由值得占据篇幅：

1. **Traversal from any node**——可以从任意节点开始遍历，最终仍能到达所有其他节点；适合 **round-robin**（轮转）式处理，例如操作系统的 CPU 调度。
2. **No need for special cases when inserting/deleting nodes**——因为最后一个节点指回第一个而不是 `null`，两端操作变得统一。这**直接消掉了**上面 `addLast` / `removeFirst` 里的那些特殊情况。
3. **Efficient queue implementation**——可高效实现队列（尤其是循环队列），不需要搬移数据；在列表未满时管理 front 和 rear 指针很容易，也没有溢出风险。

**树（第 25–28 页）** 以逐步展开的图引入——`depth: 0` 的 root，然后 `depth: 1`、`2`、`3`，每个 `TreeNode` 持有 `parent`、`element` 以及一个 **children 的 Collection**。这是递归友好、非线性的结构第一次出现，为后续的树课程做铺垫。

**收尾的联系（第 29–31 页）。** 无论哪种 ADT，操作都会反复出现：

- **Insertion / removal** of data elements —— 插入／删除数据元素
- **Iteration / traversal** of data elements —— 迭代／遍历数据元素
- **Search** for a specific data element —— 查找特定元素

这三条才是本单元真正的索引：后面遇到的每一种 ADT，都会被衡量"它支持这三类操作有多高效"——**而这，正是第一、二部分那套复杂度分析的用途。** 课件以总结收尾：行为契约与实现分离；用接口在 Java 中规定 ADT；泛型；实现；共性操作。

两次课都是复习性质，这里把他明确预警的点集中列出：

1. **推导"向已排序链表插入"的 O(n²) 复杂度。** 他讲了两次：这会是一次练习，而且是 **"a fair exam question"**。他的重点：AI 可以**帮忙**，但你必须能**准确地把问题描述给 AI**，并且能自己复现推导。**"If you just rely on AI, there's no AI in the exam."** 推导就是 n/2 次平均比较 × n 次插入的等差级数，得到 n²/4。
2. **`n ← 64`、`k ← k * 2` 那个双层循环**（课件第 29 页）。**不要**读成 O(n²)。要能说明 k 翻倍如何产生等比级数、从而约为 2ⁿ、从而 585 年。

5. **一小时的预算问题。** 要能把复杂度类别换算成"固定预算内能做多少活"：4×10⁸·n 约 900 万次，而 2ⁿ 只有 **31 个元素**。

## 第五部分 — 精简复习卡

**六句话的思维模型**

1. 把 **running time** 与 **space usage** 都当作输入规模 n 的函数来度量。
2. **平均情况不可知**（用户行为会漂移），**最坏情况可形式化**（负载有界），所以分析最坏情况。
3. **实验法**只有在锁定硬件、软件、输入数据时才诚实，而且要付实现成本；**理论法**用伪代码和基本操作，与环境无关，还能证明最优性。
4. 以恒定代价数 **primitive operations**（赋值、算术、比较、数组索引、调用、返回），忽略语言与机器差异。
5. 得到的结果是 **growth rate**——算法本身的内在属性，硬件只能给它乘一个常数。
6. **Big-O** 用上界给增长率排序；**常数因子与低阶项被丢掉**，因为它们在渐近上无关——也因为它们可以用硬件买掉。

**复杂度类别，按增长递增**

`1` < `log n` < `n` < `n log n` < `n²` < `n³` < `2ⁿ` < `n!`

**容易混淆的几对**

| | |
|---|---|
| `←` 赋值 vs `=` 相等判断 | 伪代码约定 |
| `T(n)` 绝对运行时间 vs 增长率 | 增长率与机器无关 |
| 挂钟时间 vs **进程 CPU 时间** | 共享机器上只有 CPU 时间才是公平度量 |
| 常数**在渐近意义上**可忽略 | 但在小 n 上决定胜负——所以内核里用线性查找 |
| 近似解 vs 无解 | TSP：最近邻几秒内给出 10% 以内的解，而穷举根本不可能完成 |

## 第六部分 — Glossary 术语表

| Term | 中文 | 说明 |
|---|---|---|
| **Abstract Data Type (ADT)** | 抽象数据类型 | 一种**行为契约**——规定一个类型支持哪些操作，而隐藏实现。在 Java 中用 `interface` 规定。提供封装与隔离，不同实现可以互换。 |
| **Running time** | 运行时间 | 算法耗时随输入规模变化的函数。随输入规模增长。 |
| **Space usage** | 空间占用 | 算法存放中间结果所需的内存。随实现方式剧烈变化，尤其是迭代与递归之别。 |
| **Worst case** | 最坏情况 | 最大可能的资源需求。之所以选它做分析，是因为它的上界**可知**（例如每天 24 小时视频、每只股票每秒都在交易），而平均情况不可知。 |
| **Average case** | 平均情况 | 典型输入下的期望资源消耗。实践中极难可靠确定，因为用户行为随时间变化（Google 查询、iPhone 的例子）。 |
| **Best case** | 最好情况 | 最小资源需求。课件中作为计时分布的最低条出现；不是分析目标。 |
| **Growth rate** | 增长率 | 运行时间随输入规模如何缩放（例如输入翻倍时时间是翻倍还是四倍）。是**算法本身的内在属性**，与硬件无关。 |
| **Complexity class** | 复杂度类别 | 算法的代价函数所属的渐近族——O(1)、O(log n)、O(n)、O(n log n)、O(n²)、O(n³)、O(2ⁿ)、O(n!)。 |
| **Experimental (empirical) study** | 实验（经验）研究 | 实现算法、用不同输入运行、把实测时间画成图。只有在硬件、软件、输入数据完全一致时才公平。 |
| **Theoretical analysis** | 理论分析 | 从高层描述或伪代码推导复杂度类别，不做实现。与环境无关，且能证明最优性。 |
| **Pseudo-code** | 伪代码 | 有结构、像程序但不能编译的记号：比英文有结构，比程序少细节。用缩进代替花括号，`←` 表示赋值，`=` 表示相等。 |
| **Primitive operation** | 基本操作 | 伪代码中可识别的基本计算——赋值、算术、比较、数组索引、方法调用、对象引用、返回。假设耗时为**常数**。 |
| **Constant time** | 常数时间 | 代价与输入规模无关（例如数组索引：算出地址、取值）。 |
| **O(1) — Order 1** | 常数阶 | 常数时间复杂度。 |
| **O(log n) — Logarithmic** | 对数阶 | 例如有序表上的二分查找：1,000 个元素约需 10 步，因为 2¹⁰ = 1,024。log n 增长极其缓慢。 |
| **O(n) — Linear** | 线性阶 | 必须访问每个元素（例如打印列表、扫描求最大值）。输入翻倍，时间翻倍。 |
| **O(n log n) — N-Log-N / linearithmic** | 线性对数阶 | 优秀排序算法（merge sort）的复杂度。略高于线性；小 n 时在图上几乎像直线。 |
| **O(n²) — Quadratic** | 平方阶 | 例如矩阵转置／拷贝（要搬 n² 个元素）、插入排序（n²/4）。 |
| **O(n³) — Cubic** | 立方阶 | 三层等长嵌套循环；三维结构的 n·m·l 元素计数。 |
| **O(2ⁿ) — Exponential** | 指数阶 | 例如枚举所有 n 位布尔函数。2⁵¹² ≈ 10¹⁵⁴，已超过宇宙年龄（4.42 × 10¹⁷ 秒）。 |
| **O(n!) — Factorial** | 阶乘阶 | 例如旅行商问题的穷举搜索。比指数增长更快。 |
| **Travelling Salesman Problem (TSP)** | 旅行商问题 | 每个城市访问一次并返回，最小化总路程。路线数为阶乘级。1980 年代 PC 约能处理 16 个城市；即便快 100,000 倍，今天也只有约 20 个；30 个永远不可行。真实场景：打印机字头路径、芯片布线、机器人。 |
| **Approximate solution / heuristic** | 近似解／启发式方法 | 以极低成本得到接近最优的答案——例如最近邻路线，几秒内给出与最优相差约 10% 的解。"You can't have a perfect solution, but you can have a good one." |
| **Asymptotic analysis** | 渐近分析 | 描述函数在 n → ∞ 时的极限行为。实践关注大 n（百万、十亿量级），此时低阶项与常数因子可以忽略。 |
| **Lower-order term** | 低阶项 | 增长慢于主导项的项（例如 n + 1000 里的 `+1000`，或 3n³ + 20n² + 5 里的 `20n²`）。在渐近分析中被丢弃；只在小 n 时重要。 |
| **Constant factor** | 常数因子 | 乘性的系数（例如 7n 里的 7）。被忽略，因为它不改变增长率——也因为更快的硬件可以把它抵消掉。 |
| **Big-O notation** | 大 O 记号 | 若存在正常数 c 与 n₀ 使得对所有 n ≥ n₀ 有 f(n) ≤ c·g(n)，则称 f(n) is O(g(n))。给出增长率的**上界**，并据此给函数排序。 |
| **c and n₀** | 常数 c 与阈值 n₀ | Big-O 证明中的两个见证量：c 是倍数，n₀ 是使不等式从此成立的那个输入规模。 |
| **Log-log plot** | 双对数坐标图 | 画 log f(n) 对 log n。d 次多项式成为**斜率为 d 的直线**，所以 n³ 与 n³/10⁶ 看起来平行，只差一个常数偏移。 |
| **Time budget** | 时间预算 | 固定可用时间，问能做多少活：4×10⁸·n 一小时完成 900 万次操作，而 2ⁿ 只完成 **31** 个。 |
| **Branch prediction / misprediction** | 分支预测／预测失败 | CPU 依据历史模式投机猜测 `if` 会往哪边走。猜错约损失 5 ns，因为投机做的工作被丢弃。 |
| **Pipelining** | 流水线执行 | 重叠指令的各阶段，让空闲的 CPU 资源也被利用——像工厂流水线在上一道工序完成前就准备下一道。 |
| **Cache (L1 / L2)** | 缓存 | 靠近 CPU 的高速存储。L1 约 0.5 ns，L2 约 7 ns，主存约 100 ns。取一个值会连带拉入一整块数据，以利用局部性。 |
| **Primitive operation cost table** | 基本操作耗时表 | 课件第 35 页的基准集：L1 0.5 ns、分支预测失败 5 ns、L2 7 ns、互斥锁 25 ns、主存 100 ns、压缩 1 KB 3,000 ns、磁盘寻道 10 ms、加州→荷兰→加州 0.25 s。 |
| **Disk seek** | 磁盘寻道 | 约 10 ms（1980 年为 30 ms）——由盘片转速主导，这就是它几十年几乎没改进的原因。 |
| **Generics / erasure** | 泛型／类型擦除 | 客户端写 `Stack<T>`，但编译期类型参数被代入（`Stack<String>` → `push(String)`），运行期不再存在。 |
| **Behavioural contract** | 行为契约 | ADT 承诺支持的操作集合，与它如何实现相分离。 |
| **Encapsulation** | 封装 | 把实现细节藏在接口之后。 |
| **Concrete data type** | 具体数据类型 | ADT 的实际实现，例如实现 `Stack` 的 `StackImpl`。 |
| **Linked structure** | 链式结构 | 由节点构成、每个节点持有元素与一个或多个链接的数据结构，与连续的数组相对。 |
| **Singly linked list** | 单向链表 | 节点持有 `element` 与 `next`。只能单向遍历；反转麻烦；在给定节点前插入需要遍历。 |
| **Doubly linked list** | 双向链表 | 节点持有 `prev` 与 `next`。可双向遍历、可便捷地在节点前插入、易于反转、天然适合 deque——代价是每节点额外内存与更复杂的指针维护。 |
| **Circularly linked list** | 循环链表 | 最后一个节点指回第一个。可从任意节点开始遍历；两端操作没有特殊情况；非常适合轮转调度与循环队列。 |
| **Deque** | 双端队列 | 支持在两端插入与删除的队列，天然适合双向链表实现。 |
| **Tree** | 树 | 由 `TreeNode` 构成的层次结构，每个节点持有 parent 引用、element 以及一个 children 集合；根位于 depth 0。 |
| **ADT commonalities** | ADT 共性操作 | 每种 ADT 都倾向支持的操作：插入／删除、迭代／遍历、查找特定元素。 |
| **arrayMax vs sort（性价比陷阱）** | 简便但有代价的写法 | 扫描一次求最大值是 O(n)；先排序再取最后一个是慢的，尽管因为 `sort` 是库函数而写起来容易得多。 |
